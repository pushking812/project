## 1. Главный вывод: архитектура в ТЗ не та

ТЗ предполагало `ctx.root`, `ctx.state.history`, `ctx.historyFile`, `ctx.watches` — как в монолите `ask-code.mjs`. Фактический сервер устроен иначе:

| В ТЗ (монолит) | В реальности (сервер) | Следствие |
|----------------|----------------------|-----------|
| `ctx.root` per-request | `config.root` глобальный | Смена корня = `config.root = newRoot` + остановка общего |
| `ctx.memoryDir`, `ctx.historyFile` | вычисляются от `config.root` при каждом запросе | Пересчёт не нужен |
| `ctx.state.history` | сессии per-folder (`/sessions?folder=`) | `ctx.state.*` вообще нет |
| `ctx.watches`, `ctx.browser` | глобальные `app.*` | Остановка через `app.apps`, `app.browser`, `app.watches` |

**Это упрощает, а не усложняет.** Пункты 4.5 (пересчёт `memoryDir`/`historyFile`/`ctx.state`) из ТЗ можно вычеркнуть. Вместо них — тест: после смены корня `/memory`, `/sessions`, `/notes`, `/health` отвечают про новую папку.

## 3. Противоречия — как разрешить

### 3.1. `$HOME` в allowlist

- **Default:** разрешены любые подпапки `$HOME`; сам `$HOME` запрещён как корень → `403 home_forbidden`.
- **`exit(1)` при старте** — только если `ASK_ALLOWED_ROOTS` **явно** задан и содержит `/`, корень диска или `$HOME`. Если переменная не задана — default безопасен, `exit(1)` не нужен.

### 3.2. Порядок проверок в `POST /workspace`

Строгий порядок (первое совпадение выигрывает):

1. `400 invalid_path` — не строка, пустая, control chars.
2. `403 system_path` — `/etc`, `/usr`, `/var`, `C:\Windows`, `C:\Program Files*`, `C:\ProgramData`, корень диска.
3. `403 home_forbidden` — `$HOME` сам по себе.
4. `403 not_allowed` — вне allowlist.
5. `404 not_found` — не существует / не директория.
6. `409 tasks_running` — есть активные задачи.
7. `403 plan_mode` — режим `plan` (проверять **до** всех остальных, кроме `400`).

`/etc` получит `system_path` (п. 2), а не `not_allowed` — это исправляет противоречие с критерием приёмки.

### 3.3. Один `session_id` vs per-folder

Хранить **словарь** `{root → session_id}` в файле автосессии:

```json
{
  "sessions": {
    "/home/user/project-a": "abc-123",
    "/home/user/project-b": "def-456"
  },
  "default": "abc-123"
}
```

При смене корня — брать сессию для нового корня; если нет — создать новую (или stateless, если `ASK_SESSION_AUTO=false`).

### 3.4. 409 «уже текущая»

Возвращать **`200 {ok: true, already_current: true, session_id}`** вместо 409. Для клиента это успех — он просто хотел убедиться, что сессия активна. 409 оставить только для реальных конфликтов (например, сессия занята другой задачей).

## 4. Риски — как адресовать

### 4.1. Автосессия + параллельные задачи

- **Primary:** при `409 lockSession` → retry **без сессии** (stateless). Пользователь получает результат, просто без истории. Лог: `[WARN] [session] locked, falling back to stateless`.
- **Secondary:** `start_task` не использует автосессию вообще (только `execute`). Параллельные `start_task` — каждая своя stateless-задача.
- **Document:** «параллельные задачи в одной сессии конфликтуют; для параллелизма используйте `start_task` (stateless) или явные разные `session_id`».

### 4.2. Рост истории

- Порог: `20` запросов **или** `50_000` токенов (по `estimateTokens`).
- При превышении — авто-`/compact` перед следующим запросом.
- Env: `ASK_SESSION_MAX_REQUESTS=20`, `ASK_SESSION_MAX_TOKENS=50000`, `ASK_SESSION_AUTO_COMPACT=true`.
- Лог: `[INFO] [session] auto-compact (20 requests, 48k tokens)`.

### 4.3. Смена корня во время `/ask`

`tasks_running` смотрит только реестр задач (`/start`, `/execute`). Идущие потоки `/ask` и `/browser` в него не входят.

**Решение:** добавить счётчик `activeRequests`:
- `+1` при старте `/ask`, `-1` при завершении (в `finally`).
- `+1`/`-1` для `/browser` (кроме `handoff`, где долго).
- `POST /workspace` проверяет `activeRequests === 0` (объединить с `tasks_running` → `409 code: "requests_running"`).

### 4.4. Смена корня + замки сессий

Покрывается проверкой `tasks_running` (задача, которая держит замок, — активна). Добавить тест: start task → try workspace change → 409 → task done → workspace change → 200.

### 4.5. Расширение прав

- `POST /workspace` **запрещён в `plan`** (Q5).
- Логировать каждую смену: `[INFO] [workspace] root changed: X → Y (by request)`.
- Document: «любой, кто достучится до `127.0.0.1:8737`, может менять корень в пределах allowlist; API не аутентифицирован по дизайну».

### 4.6. `files` и секреты

`isSecret` по имени ловит `.env`, `id_rsa`, `*.key`, но не `config.json` с ключом внутри. Это **известное ограничение** — задокументировать:

> «Файлы с именами, похожими на секреты (`.env`, ключи, сертификаты), блокируются. Файлы с секретами внутри, но безобидными именами (`config.json`) — **не блокируются**; используйте конвенцию `.env` или проверяйте вручную.»

Опционально (этап 6): контентные эвристики (`"api_key":`, `"password":`, `-----BEGIN`, …) с предупреждением, а не блокировкой.

### 4.7. `output_files`

**Блокер.** Нужно выяснить, как модель создаёт `.xlsx` в `/execute`:

- Если `write_excel`/`write_word` — отдельные tools в `doTool` → добавить в `ctx.writtenFiles`.
- Если через `write_file` с бинарным содержимым → `write_file` уже отслеживается, ничего не делать.
- Если никак (модель не может создать `.xlsx` в `/execute`) → `output_files` не будет работать для Office; документировать.

Способ проверки — §5.3.

### 5.2. Как Cline передаёт `files`

Два способа:
- **Документация Cline** — раздел про MCP tools, параметры-массивы.
- **Практический тест:** запустить `npx @modelcontextprotocol/inspector python mcp/server.py`, вызвать `ask` с `files: ["a.txt"]`, посмотреть, что приходит в Python (строка или объект).

Если объект — адаптировать сигнатуру Python (`files: list[dict]`). Если строка — текущее ТЗ верно.

### 5.3. `output_files` в `doTool`

```bash
# Есть ли write_excel/write_word в executor?
grep -nE "write_excel|write_word|edit_word" lib/executor.mjs mcp/ask_mcp/tools/office.py vendor/ASK.md
```

Три возможных исхода:
- **Найдено в `doTool`** → добавить в `ctx.writtenFiles`, всё работает.
- **Найдено только в Python `office.py`** → модель в `/execute` не может создавать Office-файлы; `output_files` только для `write_file`.
- **Не найдено нигде** → задокументировать ограничение.
