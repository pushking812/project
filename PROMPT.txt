# Задача: реализовать Node.js-часть проекта ask-code-mcp (этап 1)

## Контекст

Ты реализуешь **Node.js HTTP/SSE сервер** — исполняющий слой проекта `ask-code-mcp`. Полное техническое задание приложено отдельно (файл `TZ-stage1.md`, см. §4 «Контракт Node API» и §10 «План коммитов»). Твоя задача — реализовать **только Node.js часть**: коммиты 1–9 из §10. Python MCP-слой (коммиты 10–15) делает другой разработчик, тебя он не касается.

## Что уже есть

- Файл `ask-code.mjs` (монолит CLI, ~3000 строк) — его нужно положить в `vendor/ask-code.mjs` **байт-в-байт** без изменений. Скачать: `curl -fsSLo vendor/ask-code.mjs https://ask.oryxml.com/v1/code/ask-code.mjs` (если сайт недоступен — уточни у пользователя, он даст файл).
- Монолит экспортирует ~40 утилит (`gatherNotes`, `readMemory`, `folderNow`, `memoryDir`, `stepNote`, `Apps`, `NOTES_CHARS`, `MEMORY_CHARS`, `safe`, `tx`, `setLang` и др.) — их можно импортировать напрямую.
- **Не экспортированы** (нужно добавить `export` через `build/patch.mjs`): `api`, `events`, `doTool`.

## Что нужно сделать

Реализовать Node.js-сервер по ТЗ (§3–§9, §10 коммиты 1–9). Ключевое:

1. **`build/patch.mjs`** — идемпотентный патч, добавляет `export` к `api`, `events`, `doTool` в `vendor/ask-code.mjs`, пишет в `build/ask-code-core.mjs`.
2. **`ask-code-server.mjs`** — HTTP-сервер на `node:http`, 7 эндпоинтов:
   - `GET /health`
   - `GET /me`
   - `POST /ask` (SSE, `/v1/ask` + контекст проекта)
   - `POST /execute` (SSE, полный цикл `/v1/code` + `doTool`)
   - `POST /start` (async, `taskId`)
   - `GET /status/:id`
   - `POST /stop/:id`
3. **`lib/`** — модули: `config.mjs`, `log.mjs`, `sse.mjs`, `context.mjs`, `tasks.mjs`, `executor.mjs`, `mock-input.mjs`, `errors.mjs`, `ask-proxy.mjs`.
4. **`test/integration.mjs`** — интеграционные тесты, `npm test`.

## Правила работы

### Коммиты

**Ты делаешь коммиты сам.** После каждого коммита из §10 ТЗ:

1. Реализуй код согласно описанию коммита.
2. Запусти проверки, указанные в блоке «Тест» этого коммита.
3. Если проверки прошли — `git add` + `git commit -m "<сообщение из ТЗ>"`.
4. Если проверки упали — исправь, повтори, только потом коммить.

**Формат сообщения коммита:** точно как в §10 ТЗ, в стиле Conventional Commits (`feat:`, `chore:`, `test:`, `docs:`). Пример: `feat(server): SSE helper and POST /ask with project context`.

**Не сквошивай коммиты.** Каждый коммит — отдельный, самостоятельный, собираемый. История должна читаться как прогресс разработки.

**Не коммить:**
- `node_modules/`
- `build/ask-code-core.mjs` (генерируется, в `.gitignore`)
- `vendor/ask-code.mjs` — **коммить**, это вендор-копия
- `.env`, ключи, `*.log`
- `test-proj/` и любые временные папки

### Качество кода

- **ESM** (`import`/`export`), Node ≥ 18. Никакого TypeScript, никаких сборщиков.
- **Ноль зависимостей** в Node-части, кроме уже перечисленных в `package.json` (можно `@modelcontextprotocol/sdk` и `zod` для будущего, но в этапе 1 они не нужны — не устанавливай, если не используешь).
- **`node:http`** для сервера, `node:crypto` для UUID, `node:fs/promises` для файлов.
- Никаких `console.log` — только `console.error` через `lib/log.mjs` (stdout занят HTTP).
- Все ошибки — через `lib/errors.mjs` (`sendError(res, status, message)`), формат `{"error": "..."}`.
- Все асинхронные операции — с `AbortSignal` где применимо.
- Комментарии — только там, где неочевидно. JSDoc для экспортируемых функций.

### Безопасность (проверять в каждом коммите, где применимо)

- `ASK_KEY` **никогда** не логируется, не попадает в тела ответов, не передаётся в дочерние процессы (`runCommand` уже это делает — не ломай).
- Node слушает **только** `127.0.0.1` (не `0.0.0.0`).
- `doTool` переиспользуется как есть — вся защита (секреты, path traversal, control chars) остаётся в нём.
- `mockInput` возвращает `'no'` на вопрос «Run it?» / «Выполнить?» — это защита от выполнения секретных команд без человека.

### Тестирование

- **Каждый коммит** должен проходить свой блок «Тест» из §10 ТЗ.
- Для интеграционных тестов (Commit 9) — поднимать сервер на свободном порту, гасить после.
- Для юнит-тестов (Commit 5) — мокать `api`/`doTool` через `import` с подменой (или через `node:test` + `mock`).
- **Не пропускай падающие тесты.** Если тест не проходит — либо баг в коде, либо тест неверен. Разберись, не «закомментируй».

### Стиль общения

- Работай **итеративно**: сделал коммит → показал diff → ждёшь подтверждения? **Нет.** Работай автономно до конца этапа, если пользователь не сказал иначе.
- Если что-то в ТЗ неясно — **сделай разумное предположение**, задокументируй его в `README.md` в разделе «Решения и допущения», продолжай.
- Если нашёл **баг в ТЗ** (например, эндпоинт описан противоречиво) — исправь по здравому смыслу, отметь в `README.md` в разделе «Отклонения от ТЗ».
- Если нашёл **баг в `vendor/ask-code.mjs`** — не правь его, обойди в своём коде, отметь в `README.md`.

### Что НЕ делать

- Не трогай `vendor/ask-code.mjs` — только читай и патчишь через `build/patch.mjs`.
- Не реализуй Python MCP (коммиты 10–15) — это вне твоего этапа.
- Не добавляй аутентификацию в HTTP API (только `127.0.0.1`, без токена — так в ТЗ).
- Не добавляй persistence истории задач (`historyFile`) — этап 1 stateless.
- Не реализуй браузер, watches, ресурсы MCP, промпты — этап 2.
- Не переписывай `doTool` — используй как есть через `export`.
- Не рефактори `runTask` — свой цикл в `lib/executor.mjs` (~80 строк), не трогай монолит.

## Порядок работы

1. Прочитай `TZ-stage1.md` целиком (особенно §3–§10).
2. Прочитай `vendor/ask-code.mjs` — пойми, что экспортируется, что нет, как устроены `api`, `events`, `doTool`, `gatherNotes`, `readMemory`, `folderNow`, `memoryDir`, `stepNote`, `Apps`.
3. Выполни коммит 1 (scaffold + patch), проверь, что `build/ask-code-core.mjs` содержит 3 `export`.
4. Дальше — по порядку коммитов 2–9. После каждого — тест из ТЗ, потом `git commit`.
5. На коммите 9 — прогони `npm test`, все тесты должны быть зелёными.
6. В конце — короткий отчёт: что сделано, какие отклонения от ТЗ, какие риски, что осталось на этап 2.

## Критерии готовности

- Все 9 коммитов в `main` (или в ветке `stage1-node`, если пользователь просил ветку).
- `npm test` — зелёный.
- Все 11 критериев приёмки для Node API из §9 ТЗ выполнены (пункты 1–11, 18–20).
- `git log --oneline` читается как осмысленная история из 9 коммитов.
- `README.md` содержит: установку, конфигурацию (таблица env из §6.1), примеры `curl` для каждого эндпоинта, раздел «Решения и допущения», раздел «Отклонения от ТЗ» (если были).
