## 3. Противоречия внутри ТЗ

1. **`$HOME` и allowlist.** По умолчанию allowlist равен `$HOME` (п. 4.4), а следующим правилом `$HOME` в allowlist запрещён с `exit(1)`. Предлагаю: по умолчанию разрешены любые подпапки `$HOME`, сам `$HOME` запрещён как корень (`home_forbidden`), а `exit(1)` только для явно заданного `ASK_ALLOWED_ROOTS`, где есть `/`, корень диска или `$HOME`.
2. **`system_path` и `not_allowed`.** По порядку п. 4.3 `/etc` вне allowlist получит `not_allowed`. А критерий приёмки требует `system_path`. Предлагаю проверять в таком порядке: неверный путь (400), системный путь (403 `system_path`), `$HOME` (403 `home_forbidden`), вне allowlist (403 `not_allowed`), не существует (404), идут задачи (409).
3. **Один `session_id` на весь MCP.** Сессии у нас привязаны к папке (`/sessions?folder=`). Один id в файле не подходит, когда рабочая папка меняется. Предлагаю хранить словарь «корень → id» в файле автосессии.
4. **Ошибки.** В ТЗ у `ask_session_resume` 409 «уже текущая» называется ошибкой. Для клиента удобнее вернуть успех с пометкой `already_current`, но это решение за вами.

## 4. Риски, которых в ТЗ нет

1. **Автосессия и параллельные задачи.** `createTask` берёт замок сессии (`lockSession`): вторая задача в той же сессии получает 409. Если автосессия подставляется во все `execute` и `start_task`, два параллельных вызова будут падать. Варианты: при 409 запускать без сессии; автосессия только для `execute`, а не для `start_task`; отдельная сессия на каждый вызов `start_task`. Предлагаю первый.
2. **Рост расхода.** Вся история сессии уходит в каждый запрос (`history: session.history`). Автосессия «навсегда» будет раздувать каждый запрос и тратить лимит тарифа. Предлагаю порог (число записей или размер) и автоматический `/compact`, он у нас уже есть.
3. **Смена корня во время запросов `/ask`.** Проверка «нет задач» смотрит на реестр задач. Идущие потоки `/ask` и `/browser` в него не входят. Предлагаю считать их тоже (счётчик активных запросов) или ставить на время смены короткую блокировку.
4. **Смена корня и замки сессий.** Замки привязаны к `config.root`. При смене корня задача, которая ещё освобождает замок, может снять его в другой папке. Покрывается проверкой «нет задач», но нужен тест.
5. **Расширение прав.** Тот, кто достучится до `127.0.0.1:8737`, сможет менять корень в пределах allowlist. Аутентификации нет, и ТЗ её не вводит. Предлагаю режим `plan` и `edits` не считать защитой: `POST /workspace` запретить в `plan` (как и другие изменяющие запросы) и записывать смену корня в лог.
6. **`files` и секреты.** Проверка `isSecret` по имени ловит `.env`, но не `config.json` с ключом внутри. Это известное ограничение. Стоит записать его в документацию.
7. **`output_files`.** Tools `write_excel`, `write_word`, `edit_word` есть у MCP (`office.py`), но в `doTool` ask-code (то, что делает наш `executor.mjs`) они, судя по `vendor/ASK.md`, не отдельные инструменты. Открытый вопрос 3 из ТЗ остаётся открытым: сначала надо выяснить, как модель создаёт `.xlsx` в `/execute`, и только потом проектировать `writtenFiles`.
